Kubernetes · Cheatsheet 04

Red, configuración y datos

Cómo llega el tráfico a tus Pods, cómo se encuentran entre sí, cómo reciben configuración y dónde guardan datos.

Tipos de Service DNS interno Ingress ConfigMap y Secret Almacenamiento StatefulSet

Términos de esta página

Service
Una dirección fija (IP y nombre) delante de un grupo de Pods. Hace falta porque los Pods se crean y destruyen y cambian de IP.
ClusterIP / NodePort / LoadBalancer
Los tipos de Service según desde dónde se accede: solo dentro del cluster, desde un puerto de cada máquina, o desde internet con una IP externa.
Puerto / targetPort / nodePort
El puerto del Service, el puerto del contenedor al que reenvía, y el puerto abierto en la máquina (solo NodePort).
Endpoints
La lista de IPs de los Pods a los que un Service reparte el tráfico en este momento.
DNS
El “directorio” que traduce nombres a direcciones. En el cluster, cada Service tiene un nombre DNS automático.
Ingress
Reglas para recibir tráfico web (HTTP/HTTPS) desde afuera y repartirlo por dominio o ruta entre varios Services.
Ingress controller
El programa que aplica esas reglas (Traefik, por ejemplo). Sin él, un Ingress no hace nada.
ConfigMap / Secret
Objetos para guardar configuración (ConfigMap) y datos sensibles como contraseñas (Secret), separados de la imagen.
PersistentVolumeClaim (PVC)
Un pedido de disco (“quiero 1 GB”). El cluster lo cumple creando un PersistentVolume (PV), el disco real.
StorageClass
El “proveedor” de discos del cluster: sabe crear PVs automáticamente cuando aparece un PVC.
StatefulSet
Como un Deployment, pero para apps con datos propios por réplica (bases de datos): nombres fijos y un disco para cada una.

Tipos de Service y sus puertos

Cada tipo agrega una capa sobre el anterior.

¿Cuál uso?

TipoAccesible desdeUso típico

Los 4 puertos

CampoDóndeEjemplo
containerPortDeployment: donde escucha la app3000

El error más común: targetPort distinto del puerto real de la app. El Service existe pero responde connection refused.

2

DNS interno

Cada Service tiene un nombre resoluble desde cualquier Pod. Igual que el nombre de servicio en compose.

Formas del nombre

NombreFunciona desde
monguitoPods del mismo namespace
monguito.datosCualquier namespace (<service>.<namespace>)
monguito.datos.svc.cluster.localNombre completo (FQDN)
 
mongodb://mati:<password>@monguito:27017/miapp?authSource=admin
✓

Si el Service de Mongo se llama monguito, tu app.js no cambia al pasar de compose a Kubernetes.

Probar la resolución

kubectl run tmp --rm -it --image=busybox -- nslookup monguito
Crea un Pod temporal y pregunta al DNS del cluster qué IP tiene el nombre monguito. Si responde con una IP, el Service existe y el nombre funciona; si dice can't resolve, el Service no existe, tiene otro nombre o está en otro namespace (entonces el nombre es monguito.<namespace>).
kubectl run tmp --rm -it --image=busybox -- wget -qO- http://chanchito
Hace una petición HTTP al Service desde adentro del cluster y muestra la respuesta. Si responde acá pero no desde tu PC, el problema está en cómo lo exponés (NodePort, port-forward, Ingress), no en la app.
kubectl get endpoints chanchito
Muestra las IPs y puertos de los Pods a los que el Service manda tráfico. Si aparece <none>, el Service no encontró Pods: o el selector no coincide con las etiquetas de los Pods, o los Pods todavía no están Ready.

ConfigMap y Secret: tres formas de usarlos

Como variables sueltas, como todas las variables juntas, o como archivos.

env (una variable)

env:
  - name: MONGO_PASSWORD
    valueFrom:
      secretKeyRef:
        name: mongo-secret
        key: MONGO_PASSWORD
  - name: MONGO_HOST
    valueFrom:
      configMapKeyRef:
        name: chanchito-config
        key: MONGO_HOST

envFrom (todas)

envFrom:
  - configMapRef:
      name: chanchito-config
  - secretRef:
      name: mongo-secret
i

Armar la URL con variables: value: mongodb://$(MONGO_USER):$(MONGO_PASSWORD)@monguito:27017/miapp?authSource=admin (declarando antes las variables).

Como archivos

containers:
  - name: chanchito
    volumeMounts:
      - name: config
        mountPath: /etc/config
        readOnly: true
volumes:
  - name: config
    configMap:
      name: chanchito-config
!

Si cambiás un ConfigMap/Secret, las variables de entorno no se actualizan solas: hacé kubectl rollout restart deploy/chanchito. Los archivos montados sí se actualizan (con algo de demora).

Almacenamiento: PVC → PV → disco

El Pod pide, el cluster provee. Vos normalmente solo escribís el PVC.

accessModes

ModoSignificado
ReadWriteOnce (RWO)Lectura/escritura desde un nodo. Lo normal para DBs
ReadOnlyMany (ROX)Solo lectura desde varios nodos
ReadWriteMany (RWX)Escritura desde varios nodos (requiere NFS o similar)
ReadWriteOncePodUn único Pod

Comandos y cuidados

kubectl get pvc
kubectl get pv
kubectl get storageclass
PVC debe quedar Bound. Si queda Pending: no hay StorageClass default o no hay espacio.
!

Con reclaimPolicy: Delete (el default en la mayoría), borrar el PVC borra los datos. kubectl delete -f k8s/ incluye el PVC si está en esa carpeta.

i

emptyDir: volumen temporal que vive lo que vive el Pod (caché, archivos compartidos entre contenedores del mismo Pod).

6

Deployment vs StatefulSet

Para una base de datos con réplicas, StatefulSet.

Diferencias

DeploymentStatefulSet
Nombres de PodsAleatorios (-x2k4)Fijos y ordenados (-0, -1)
DiscoUn PVC compartidoUn PVC por réplica (volumeClaimTemplates)
Orden de arranqueTodos a la vezDe a uno, en orden
DNS por PodNoSí, con Service headless
Ideal paraAPIs, frontends, workersMongo/Postgres con réplicas, Kafka
✓

Para aprender y en local, Mongo con Deployment + PVC + 1 réplica alcanza. En producción, mejor una base gestionada o un operator.

StatefulSet mínimo

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: monguito
spec:
  serviceName: monguito          # Service headless
  replicas: 1
  selector:
    matchLabels: { app: monguito }
  template:
    metadata:
      labels: { app: monguito }
    spec:
      containers:
        - name: mongo
          image: mongo:7
          ports: [{ containerPort: 27017 }]
          volumeMounts:
            - { name: datos, mountPath: /data/db }
  volumeClaimTemplates:          # un PVC por Pod
    - metadata: { name: datos }
      spec:
        accessModes: [ReadWriteOnce]
        resources: { requests: { storage: 1Gi } }
